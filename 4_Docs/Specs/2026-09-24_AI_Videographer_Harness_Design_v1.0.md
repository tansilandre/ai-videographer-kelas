# AI Videographer Harness — Design v1.0

**Date:** 2026-09-24 · **Status:** approved direction (Approach A), built in rounds
**Owner:** the owner · **Written by:** Claude (Opus 5.5)

---

## 1. Goal

A folder-based **AI Videographer agent** that any capable agent (Claude Code, Tencent WorkBuddy,
Codex, Cursor) can run end to end, and that can be copied to a new workspace or published on GitHub.

It turns a client brief into short-form social video through a fixed, consistent pipeline:

```
brief → scenes & shot list → reference sheets (character / location / product)
      → storyboard panels → first + last frame per shot → video prompts
      → ✋ VIDEO GATE (human approves, cost shown) → video clips → edit (extra)
```

## 3. Pipeline stages and skills

One skill per job, as the owner listed them, plus an orchestrator and a setup skill.

| Stage | Skill | Output | Spends credits? |
|---|---|---|---|
| 0 | `vg-setup` | doctor report: python, ffmpeg, node, key, balance | no |
| — | `vg-director` | **entry point**: runs the stages in order, enforces gates | — |
| 1 | `vg-scene` | `1_Script/Shotlist.json` + script from the brief | no |
| 2 | `vg-image-prompt` | prompts for sheets, panels, frames (gpt-image-2 formula) | no |
| 3 | `vg-reference-sheets` | character / location / product sheets | images |
| 4 | `vg-storyboard` | one panel per shot, then first + last frames | images |
| 5 | `vg-image` | how to call `vg image`, check the result, iterate | images |
| 6 | `vg-video-prompt` | per-shot video prompt, dialogue fit, mode payload | no |
| 7 | `vg-video` | estimate → gate → pilot → batch → download | **video** |
| 8 | `vg-edit` | rough cut, captions, motion graphics, final export | no (local) |

WorkBuddy reportedly ignores a project-level `AGENTS.md`, so every rule that matters is repeated
inside `vg-director/SKILL.md`. `AGENTS.md` is a short pointer to it.

### Shot modes (D4)

Gemini Omni Flash rejects `first_frame_url` together with `character_ids`, `audio_ids`,
`image_urls` or `video_list`. So each shot declares one mode:

| Mode | Payload | Use for |
|---|---|---|
| `frames` | `first_frame_url` (+ `last_frame_url`) | b-roll, locations, product, transitions — exact composition |
| `character` | `character_ids` + `audio_ids` + storyboard panel as `image_urls` | talking UGC shots — same face and voice every shot |
| `text` | prompt only | fallback / cheap exploration |

The tool validates the mode before sending, so an illegal combination never reaches the API.

### Dialogue fit rule

From an early diagnosis (audio truncated mid-sentence at 4 s on a talking shot):
`characters_of_dialogue ≤ (duration_s − 0.7) × 10.5`. The tool picks the shortest allowed duration
(`4/6/8/10`) that fits, and refuses a shot whose line does not fit 10 s.

## 4. Credit safety (checkpoints)

Six layers, from cheapest to strongest. Layers 1–5 are enforced **in code**, so a weaker model
that skips instructions still cannot burn credits.

1. **Dry run** — every paid command takes `--dry-run`: prints a summary (model, params, input
   files, a shortened prompt, cost), not the exact request payload, and calls nothing.
2. **Local validation** — model rules (field names, types, exclusivity, 7-unit media quota,
   dialogue fit), per-target image aspect/resolution combinations, `file:` refs that try to leave
   the project folder, assets nothing uses, and dialogue outside character mode (an unlocked voice)
   are all checked before any request or at `validate` time.
3. **Idempotency and resume** — each generation has a key = hash(model + payload + input file
   hashes). The ledger entry is written the moment a `taskId` comes back, *before* polling.
   - Same key already succeeded and file exists → skip, spend nothing.
   - Same key pending (crash, timeout, closed laptop) → resume polling that `taskId`, never re-submit.
   - A deliberate new take needs `--new-take`, which also bumps the file version.
4. **Budget caps** from `.env`: `VG_BUDGET_PROJECT` (total per project) and `VG_MAX_PER_CALL`.
   A call that would cross a cap is refused. Balance is checked before every paid call.
5. **Video gate (D2)** — `vg video` refuses to run unless `project.json` holds a matching, unused
   approval for those shots. `vg approve video` stores a **snapshot hash** of each approved shot's
   frames, prompt, mode and duration plus the estimate shown. If anything changes after approval,
   the hash no longer matches and the shot needs approval again. The director skill calls
   `vg approve` only after the owner says yes in chat, having shown the estimate first — the pilot
   shot's own cost next to the total for all shots — and recommends approving that **pilot shot**
   before the rest, at its own cost; approving the remainder afterward is a new question for its
   own remaining total, using the same `--shots`/`--all` it was approved with.

   `--confirm` must equal the total the owner actually agreed to for exactly the shots being
   approved in that call, not whatever the tool happens to print — if the two disagree, the agent
   stops and asks again rather than resubmitting with the printed number. Approval itself is a
   **human-typed confirmation**, not just a CLI flag: by default (`VG_APPROVAL_MODE=terminal`, set
   only in `.env`) `approve` prints the shot table, then asks for a random 4-digit code on the real
   terminal (`/dev/tty`). An agent's shell has no terminal, so it is refused with the exact command
   to hand the owner — which starts `cd '<workspace>' && python3 2_Tools/vg/vg.py approve video -p
   <project> ...` (keeping `--new-take`/`--resolution`/`--allow-untested`) — and only the owner,
   typing on their own terminal, can complete the approval. **Never run `vg approve` through
   script, expect, a pty, tmux or any terminal the agent controls; only the human types the code.**
   An agent may open the command in the human's own terminal panel for them, but the human types
   the code — this is friction against accidental or casual approval, not a wall against a
   deliberately hostile agent (see Honest limits below). `VG_APPROVAL_MODE=chat` is a weaker
   fallback for a setup with no terminal (e.g. a messaging app), where the agent may call `approve`
   itself right after an explicit yes — this exists for reachability, not because it is as strong
   as the terminal path.

   Each approval is **single-use**: it pays for exactly one take of one shot and is marked used the
   moment `vg video` spends it — including a take that then **fails** at the provider, so a retry
   needs its own new yes and its own approval too, not just `--new-take`. A re-roll of an existing
   clip is a new charge needing its own new yes and its own approval (`--new-take` on both `approve`
   and `video`) — an old, unchanged-snapshot approval does not cover it. The ledger tracks a row
   through `submitting` (written before the call reaches kie.ai) → `pending` → `success`/`fail`, or
   `rejected` (kie.ai definitely refused; nothing charged; a video approval it consumed is restored)
   or `unknown` (a network error left the outcome unclear). A target stuck `submitting`, `unknown`,
   or a `pending` row that can never finish, is blocked from further attempts until the owner checks
   the kie.ai dashboard: the task is there → `vg adopt -p <project> --target <kind:id> --task-id
   <id>` so `vg resume` downloads it instead of anyone paying again; nothing was created → `vg
   release -p <project> --target <kind:id>`, which marks the row `abandoned` (still counted toward
   the budget at its estimate). Either way a video target still needs a brand new approval.

   **Honest limits:** this layer stops accidental or casual approval — a slip of a flag, an agent
   assuming consent, a stale approval reused. It does not stop a deliberately hostile or compromised
   agent that is willing to lie about what a human said, since the code only proves *someone* typed
   it on the terminal at that moment. The actual hard wall against runaway spend is layer 6 below: a
   dedicated kie.ai key with its own capped balance, so the worst case is bounded by the cap, not by
   how well this layer holds.
6. **kie.ai key cap** (outer net) — kie.ai/api-key lets you set an hourly, daily or total credit
   limit per key. Use a dedicated key with a total cap for the harness; this is the limit that holds
   even if every check above were somehow bypassed.

Also: results are downloaded immediately (kie.ai URLs expire in 1–14 days, and the docs contradict
each other), and every task's `creditsConsumed` is written to the ledger so estimates and actual
spend can be compared.

### Adversarial review, 2026-09-24

A pass assuming a hostile or merely careless agent, not just an honest one, found and fixed:

- Duplicate shot ids in `Shotlist.json` could be billed twice under one id.
- Two concurrent `vg` processes could both pass the busy check and both submit for the same target.
- A timeout that happened *after* kie.ai had already accepted the task could cause a retry that
  paid twice for one clip.
- A `--confirm 0` (or otherwise zero-credit) approval could re-arm a shot that had already spent
  its approval.
- A clip generated with `--new-take` wasn't being counted as "done" by later idempotency checks.
- A shot with a task already in flight was displayed as unpaid/unapproved instead of "already
  committed."
- A character's identity (portrait, description, or voice) could change in `Shotlist.json` after
  `vg character create` without the tool noticing, silently using a stale identity.
- The dialogue fit/word-for-word check was reading the wrong field in one code path.
- A video call that failed but was still charged by kie.ai wasn't being added to project spend.
- A same-named environment variable could raise `VG_BUDGET_PROJECT`/`VG_MAX_PER_CALL` above what
  `.env` set, since the process environment was consulted first.

All of the above are now fixed in `2_Tools/vg/`: shot ids and targets are deduplicated and
uniqueness-checked, the project lock (`.project.lock`, `flock`) serializes every submit, the
ledger row is written *before* the provider call so a crash mid-request leaves a `submitting`/
`unknown` marker instead of silence, approvals are single-use and consumed atomically inside the
same locked transaction as the submit, `--new-take` clips are tracked as their own key, in-flight
targets are reported as committed spend, character identity is hashed and compared against the
live Shotlist/portrait/voice on every video build, dialogue is checked against `video_prompt`
verbatim, charged failures are summed into `Project.spent`, and budget/approval-mode settings are
read only from `.env`, never the process environment.

## 5. The `vg` tool

`python3 2_Tools/vg/vg.py <command>` — standard library only, Python 3.9+.

| Command | What it does | Paid |
|---|---|---|
| `doctor` | checks python, ffmpeg (+libass), node, `.env`, key, balance | no |
| `credits` | balance | no |
| `new <slug>` | create a project from the template | no |
| `validate` | checks `Shotlist.json` against the schema and model rules | no |
| `upload <file>` | upload to kie.ai, cache URL by file hash (re-upload after 20 h) | no |
| `image` | text-to-image or image-to-image, poll, download, version, ledger | yes |
| `character create` | Omni identity: creates the voice first (if the character defines one), then the character — there is no separate `voice create` command | yes* |
| `estimate` | cost of a stage from Shotlist + model pricing | no |
| `approve video` | record the gate approval + snapshot, gated behind a human-typed confirmation code | no |
| `video` | gated, validated, idempotent video generation | **yes** |
| `resume` | poll every pending task in the ledger; flag any stuck `submitting`/`unknown` row, naming both `adopt` and `release` | no |
| `release` | human-only: after checking kie.ai shows nothing was created, unblock a target stuck `submitting`/`unknown`/`pending` (row becomes `abandoned`, still counted toward budget) | no |
| `adopt` | human-only: after checking kie.ai shows a task *was* created, attach its task id to a `submitting`/`unknown` row so `resume` downloads it | no |
| `status` | stage progress and spend | no |
| `board` | regenerate the HTML review board | no |
| `edit roughcut` | FFmpeg: normalise and concatenate clips in shot order; shows a shot's storyboard panel when there's no clip yet, else a dark green (`real`) / dark purple (`mg`) placeholder (does not trim) | no |

\* the cost of Omni character and voice creation is not published; the ledger records it after the
call — tell the human before every `create`, including a re-create (a changed portrait, body,
description or voice makes the stored identity stale; `video`/`approve` then refuse with exit `1`).

Ledger states a task row can be in: `submitting`, `pending`, `success`, `fail`, `rejected`,
`unknown`, `abandoned`.

### Model registry

Each model is one JSON file in `2_Tools/vg/models/`. Adding a model means adding a file: provider,
`model` id(s), field names, allowed values, types, limits, exclusivity rules, and a pricing table.
Code only changes when a **new provider** (new API shape) is added, as a new file in `providers/`.

Shipped: `gpt-image-2.json` (live-tested), `gemini-omni-flash-1-1.json` (live-tested in round 3),
`veo-3-1.json` (from docs, marked untested — proves the registry handles a second video model).

**Later (D8):** an MCP-only provider such as Higgsfield cannot be called from Python. Its registry
entry would declare `"provider": "mcp"`. `vg` then validates and estimates as usual, and hands the
agent the payload to send through the MCP tool, and `vg record` stores the result in the ledger.
Not built now.

## 6. Review board (D3)

One self-contained HTML file per project, regenerated by `vg board`. No server. Sections:

1. Header — project, stage, spend so far, last balance, video estimate, gate status.
2. References — every sheet, grouped by character / location / product.
3. Storyboard — one card per shot in timeline order: panel, source type (AI / real footage /
   motion graphic), mode, duration, dialogue, on-screen text.
4. Frames — first and last frame side by side per AI shot, with its video prompt and cost.
5. Clips — `<video>` per shot once generated, with actual credits.

Non-AI shots (real footage, motion graphics) appear as labelled placeholders so the full timeline
is visible.

## 7. Requirements and setup

`.env` (never committed, never edited by an agent — only the human): `KIE_API_KEY`,
`VG_BUDGET_PROJECT`, `VG_MAX_PER_CALL`, `VG_APPROVAL_MODE`, `VG_IMAGE_MODEL`, `VG_VIDEO_MODEL`.

`install.sh`: checks Python ≥ 3.9, ffmpeg, node ≥ 22; links `1_Skills/*` into `.claude/skills`
(project), and optionally into `~/.claude/skills`, `~/.workbuddy-ai/skills` and `~/.agents/skills`
— printing `ok` for a correct link and recreating/repointing any link that's missing or points
elsewhere (including a `--global` link left over from a different workspace); copies
`.env.example` to `.env` if missing (never touching an existing one) and sets it `chmod 600`; runs
`vg doctor`, which also warns if `.env` is readable by other users.

Edit-stage extras (only for round 4): FFmpeg with libass (`brew tap homebrew-ffmpeg/ffmpeg`),
HyperFrames (`npx hyperframes`), a whisper for word timings.

## 8. Edit stage (round 4)

- **Hyper-Motion rejected**: it animates a person from a pose video (research code on Wan2.1-14B),
  licensed CC BY-NC-SA (no commercial use), needs an NVIDIA GPU — it cannot run on this M1 Pro
  and does no editing or subtitles.
- **HyperFrames** (HeyGen, Apache-2.0): HTML + GSAP compositions, word-level captions,
  transitions, audio ducking; designed for agents.
- **FFmpeg**: normalise, concatenate, mix, loudness to −14 LUFS, final encode.
- Rough cut first (`vg edit roughcut`), then captions and motion graphics in HyperFrames.
